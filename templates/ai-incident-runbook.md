# AI 事故响应手册

> 智能体会读外部内容、调用工具、动真实数据，出事故只是时间问题。这份手册在**上线前**写好、演练一次，出事时照着做。和[智能体授权与管控清单](agent-governance-checklist.md)、[员工 AI 使用规范](ai-use-policy.md)配套使用。

## 1. 什么算 AI 事故

| 级别 | 例子 | 响应时限 |
| --- | --- | --- |
| **P1 严重** | 智能体越权删除或修改了生产数据；客户或员工个人信息泄露；以公司名义对外发送了错误或不当信息；疑似被提示注入后执行了攻击者指令；依赖包或第三方 Skill / MCP 服务器被投毒 | 立即，15 分钟内开始处置 |
| **P2 较重** | 面向客户的 AI 大面积答错；成本异常飙升（如单日费用超过预算 3 倍）；评估通过率骤降 | 4 小时内 |
| **P3 一般** | 个别错误回答；员工误把内部数据输入公共 AI 工具（未扩散） | 1 个工作日内 |

## 2. 处置步骤

### 第一步：止损（先停，再查）

- [ ] 关停开关：暂停该智能体或功能（上线前就要确认有一键关停的办法）
- [ ] 吊销或轮换它使用的 API 密钥、令牌和账号权限
- [ ] 如果是依赖或插件被投毒：确认受影响的版本和机器，**把这些机器上的所有凭证当作已泄露**并全部轮换
- [ ] 需要时切换到人工流程或降级方案

### 第二步：保全证据

- [ ] 导出完整轨迹：输入、每一次工具调用及参数和结果、最终输出、时间戳
- [ ] 保存相关的外部内容（网页、邮件、文档），提示注入往往藏在这里
- [ ] 记录模型版本、提示版本、配置和依赖版本

### 第三步：评估影响

| 问题 | 回答 |
| --- | --- |
| 影响了哪些数据、系统、客户？ | |
| 是否涉及个人信息？需要通知哪些人和监管部门？ | |
| 是否对外造成了影响（错误信息、违规内容）？ | |
| 根因属于哪一类：模型错误 / 提示注入 / 权限过大 / 工具缺陷 / 供应链 / 人为误用？ | |

### 第四步：沟通

| 对象 | 谁负责 | 时限 |
| --- | --- | --- |
| 管理层 | | P1 立即 |
| 法务、合规、信息安全 | | P1 立即 |
| 受影响的客户 / 员工 | | 按法律要求和公司制度 |
| 监管部门 | | 按适用法规 |

### 第五步：恢复

- [ ] 修复根因（收紧权限、加人工确认、修补工具、锁定依赖版本）
- [ ] 把这次事故做成评估用例，加入评估集
- [ ] 重跑评估和安全测试，全部通过后再恢复上线

## 3. 复盘（事故结束后 5 个工作日内）

不追究个人，重点找系统原因：

| 问题 | 回答 |
| --- | --- |
| 时间线（何时发生、何时发现、何时止损） | |
| 为什么监控没有更早发现？ | |
| 哪道防线本该挡住它？为什么没挡住？ | |
| 改进措施、负责人、完成日期 | |
| 是否需要调整智能体的授权等级？ | |

## 4. 上线前的准备清单

- [ ] 有一键关停的办法，并且测试过
- [ ] 凭证不放在智能体能读到的地方（Anthropic 公开的做法：把密钥留在沙盒之外，由代理服务代为调用）
- [ ] 完整轨迹日志至少保留 ____ 天
- [ ] 设置了基于动作的告警（如短时间大量删除、访问从未访问过的系统、费用突增）
- [ ] 依赖版本已锁定；第三方 Skills、插件、MCP 服务器经过审核
- [ ] 本手册的联系人和渠道已填写，并演练过一次
